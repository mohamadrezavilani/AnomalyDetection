# نخستین تحویل برنامهٔ افزایش ظرفیت Viewer

این تحویل، مبنا، مدارک آزمایش‌های پیشین، ابزار سنجش و انتخاب نخستین **آزمایش** است. نسخهٔ افزایش سرعت برای نصب روی سرور نیست. Runtime، داده، checkpoint، تاریخ شروع، روش و آستانهٔ AD و رابط کاربری تغییر نکرده‌اند.

## مبنا و جداسازی

- مبنا: `1dffd3ddbd58b11bfc5501d0e87b65d98c22344f`؛ شاخهٔ مستقل `perf/viewer-capacity-20261116` و PR30.
- Root runtime: `b7273437ea42c1aea7d0183c3020be133c84dba5735c68a01a6fd81a4b56d7c8`.
- AD: `AD-20261115-CENSUS-INTEGRITY` با hash برابر `3e3748d196b482fe978674ff367d9dfa650e93b3bf1d1651aa72601c07938b02`؛ تغییرات دقت ایجنت دیگر در این شاخه وارد نشده‌اند.
- مشخصات ساختار و ایندکس‌های **آخرین گزارش مالک در ۱۵ نوامبر**، مستقل از محیط CI، در `validation/viewer_capacity_baseline.json.gz` ثبت شده‌اند. آن‌ها وضعیت زندهٔ امروز اعلام نمی‌شوند.
- تنظیمات Writer هر lane بومی از همان اتصال خوانده شده‌اند. تنظیمات observer یا نمونهٔ قدیمی startup، جای اندازه‌گیری جاری Writer نیستند.

## مدارک V3 تا V7

فایل اصلی `P24_Performance_Agent_Handoff_20261110.zip` بررسی و HANDOFF کامل خوانده شد؛ ۱۷ فایل Manifest بیرونی تطبیق دارند. Manifestهای درونی V3/V4/V5/V6/V7 به‌ترتیب ۱۵، ۲۰، ۲۱، ۲۷ و ۲۹ فایل را بدون mismatch پوشش می‌دهند. گزارش JSON، بستهٔ کد، hash فایل‌های کد، entry pointها، فرمان PG و پنج source guard هر نسخه در رسید مبنا به هم مرتبط‌اند.

در V7، صرفه‌جویی مستقیم دو merge برابر 1.643 ثانیه است. کل merge این دو جدول 17.438 ثانیه، یعنی 8.84٪ همان اجرای قدیمی بوده؛ حتی صفرکردن کامل آن در **همان workload** سقفی نزدیک 1.097 برابر دارد. این سقف به Runtime و سرور امروز تعمیم داده نمی‌شود.

رسیدهای قدیمی ۲ پنجرهٔ seed با ۸۵٬۲۷۳ شاهد و ۴ target با ۱۷۶٬۴۲۵ شاهد دارند. hash دقیق Captureهای ورودی در آن رسیدها ثبت نشده؛ بازتولید کامل همان ورودی‌ها تأیید نشده است. هر پنج source guard آن بسته‌ها با کد مبنای کنونی فرق دارند؛ اسکریپت‌های قدیمی روی نصب جاری اجرا نشده‌اند. وضعیت «رسید اصلی بررسی‌شده» از «ورودی اصلی قابل‌بازتولید» جداست.

## بهینه‌سازی‌های موجود

lookup سراسری مرتب‌شده با chunk حداکثر ۲۰۴۸، کلیدهای binary و prefix، کش ورودی projection داخل تراکنش، COPY مرتب، انتشار تفاضلی و closure محدود به وابستگی واقعی پرداخت فعال‌اند. پیش‌خوانی Capture در مسیر forward موجود است؛ حلقهٔ history فعلاً دریافت همگام دارد. این موارد به‌عنوان قابلیت جدید معرفی نمی‌شوند.

## سنجش انجام‌شده و محدودهٔ آن

`viewer_performance.capacity.baseline` فقط دیتابیس‌های ساخته‌شده توسط همان invocation با نام `p24_design_capacity_*_qualification` را باز می‌کند؛ دیتابیس محصول را باز نمی‌کند. پروفایل اتصال، fetch، execute، COPY، commit و rollback خصوصی همان instance است و کد عمومی کلاس را monkey-patch نمی‌کند. زمان‌های exclusive جمع‌پذیرند؛ زمان inclusive متد و فرزندان SQL آن دوباره جمع نمی‌شوند.

مسیر history واقعاً از `manual_recheck` با high-watermark نگهداری‌شده استفاده می‌کند. تنظیم زمان‌بندی فقط روی دیتابیس آزمایش خودش انجام می‌شود. bootstrap، replay و recheck جدا گزارش می‌شوند. Corpus شامل ورودی عادی تازه برای RequestID موجود، پرداخت بین پنجره‌ها، نسخهٔ رقیب بین RequestIDها و ورود دیررس با زمان رویداد اصلی است.

رسید بومی: `validation/viewer_capacity_native.json.gz`، workflow `43821930036`، head برابر `bb81ca652b2ef7442d324edcb4d07f8d94ca3a83`؛ hash ZIP artifact برابر `389554eb2046e6731220634874dc6715dc7d5fd01608de8ae8b87accd3bc4c4c`. Git SHA داخل رسید، merge آزمایشی CI است؛ با base نصب اشتباه نشود.

دو جفت با ترتیب plain/profiled و profiled/plain، ۲۰ انتشار آزمایشی و ۱۰ تطبیق مرزی را ثبت کردند؛ همه برابرند. شواهد خام و provenance، مدل‌های مشتق، revision، transitionها، ledger و receipt مقایسه شدند. withdrawn پس از تعارض در هر چهار lane باقی ماند. تغییر روش یا آستانه‌ای برای سبزشدن آزمون انجام نشده است.

در نمونهٔ مصنوعی بزرگ‌تر این مجموعه، ۶٬۱۴۵ شاهد تازه و ۲٬۰۵۰ درخواست متأثر ثبت شد. زمان profiled حدود 4.18 تا 4.24 ثانیه بود؛ ingest حدود 1.23، rebuild حدود 1.29 تا 1.33، payment حدود 1.19 تا 1.20 ثانیه. این سه متد مراحل جدا هستند؛ زیرمتد merge دوباره به آن‌ها اضافه نمی‌شود. زمان plain همان گروه حدود 4.06 تا 4.10 ثانیه بود؛ سربار ابزار پنهان نشده است.

این حجم کوچک است و به نرخ سرور تبدیل نمی‌شود. cache سیستم‌عامل سرد نشده و مجموعهٔ فعال بزرگ‌تر از کش مؤثر اثبات نشده است. محدودکردن حافظهٔ container به ۱GiB چنین اثباتی نیست. صدک ۹۵ نمونهٔ کوچک، ظرفیت پرترافیک نیست.

شمارندهٔ I/O/WAL از backend خود Writer خوانده می‌شود؛ background writer، AD و دیگر اتصال‌ها به آن منتسب نمی‌شوند. انتشار تجمعی این شمارنده‌ها asynchronous است: delta آن‌ها مرز دقیق پنجره نیست و ممکن است کار قبلی همان backend را شامل شود. mutationها و buffer fetch/hit جاری پیش از commit از آمار **تراکنش خود Writer** جدا ثبت می‌شوند. خواندن PostgreSQL می‌تواند از cache سیستم‌عامل پاسخ بگیرد و معادل خواندن فیزیکی دیسک یا تعداد صفحات یکتای مجموعهٔ فعال نیست. هیچ reset آمار کلاستر انجام نمی‌شود.

## شواهد مالک و انتخاب نخستین نامزد

در گزارش هم‌نسخهٔ ۱۵ نوامبر، ۱۳۷ از ۱۵۷ نمونهٔ فعال در DataFileRead بودند. سه شکل مهم عبارت‌اند از merge جدول raw با ۲۸ نمونه، lookup موجودی Origin با ۲۴ نمونه، و COPY جدول‌های events/links با مجموع ۳۹ نمونه. این‌ها **شمار نمونه‌اند، نه سهم زمان اجرا**. فایل دیسکِ ۱۶ نوامبر متعلق به همان چرخه نیست؛ تنها شاهد مکمل است.

**C1 برای آزمایش ایزوله انتخاب می‌شود: فیلتر محدودِ عضویت Origin، فقط برای پاسخ منفیِ قطعی.** کش مثبت ساده، اولین مراجعه برای شاهدهای جدید را حذف نمی‌کند. نامزد پیشنهادی باید از snapshot کامل و دارای fence ساخته شود؛ کلید مثبت یا نامطمئن همچنان همهٔ نسخه‌ها را از مسیر معتبر فعلی بخواند. build ناقص، restart، تغییر منبع/قرارداد، maintenance یا Writer ناشناخته باید استفاده از پاسخ منفی را غیرفعال کند. bitهای Origin جدید پیش از commit اضافه می‌شوند؛ rollback فقط false-positive اضافی مجاز دارد، نه false-negative. TTL و حذف دیررس وارد طرح نمی‌شوند.

تصمیم فعلی **مجوز آزمون** است، نه حفظ نامزد در محصول. C1 هنوز پیاده‌سازی نشده است. اسکن اولیه، حافظه، محاسبهٔ hash، invalidation و rebuild باید داخل هزینهٔ مقایسه بیایند. سقف سود آن روی مالک هنوز UNKNOWN است؛ با نسبت نمونه‌های activity حدس زده نمی‌شود. در CI کوچک، حذف کامل مرحلهٔ آماده‌سازی ورودی projection فقط حدود ۳٪ سقف سود دارد؛ این حذف به‌عنوان راه‌حل ظرفیت انتخاب نمی‌شود.

C1 هزینهٔ درج و نگهداری ایندکس‌های نهایی را حل نمی‌کند. مسیر ساخت مستقل تاریخچه، ساخت ایندکس پس از بارگذاری و سازگاری reader/AD، نامزد معماری بعدی باقی است؛ نوع پارتیشن/جدول و global identity registry پیشاپیش قطعی نشده‌اند. V7 و HMAC-parallel هم‌زمان با C1 فعال نخواهند شد.

## ورودی واقعی لازم و اقدام مالک

چهار فایل ۲۰ اکتبر، مجموعاً ۳۴۹٬۹۱۰ رکورد دارند؛ metadata و hash آن‌ها ثبت شده‌اند، ولی verification لازمِ پذیرش Capture ندارند. `complete=true` به‌تنهایی proof کامل بودن snapshot نیست؛ برای ارائهٔ نرخ انتشار کامل، proof ساخته نمی‌شود.

`Collect_Capacity_Inputs.py` چهار Capture متوالیِ از قبل موجود و دارای proof را انتخاب و با نام و bytes اصلی ZIP می‌کند. config فقط با AST خوانده می‌شود؛ هیچ config، دیتابیس، Elasticsearch یا Worker اجرا نمی‌شود. scan حداکثر ۱۲ فایل، فایل gzip حداکثر ۳۲MiB، بسط حداکثر ۱۹۲MiB و bundle حداکثر ۹۶MiB دارد. این سقف‌ها ورودی ابزارند و پذیرش بودجهٔ RAM کل محصول نیستند. آرشیو خصوصی در reports نوشته می‌شود؛ هیچ Capture به GitHub افزوده نمی‌شود.

## گیت‌های باز

کش سرد/گرم و working set بزرگ‌تر از کش مؤثر، سنجش مرحله‌ای بار واقعی مالک، C1 و برابری/rollback/restart آن، مسیر جدید ذخیره‌سازی، snapshot هم‌زمان AD، ارزیابی واقعی و backlog آن، اجرای ممتد هشت‌ساعته، ظرفیت ۶۰ تا ۱۲۰ پنجره/ساعت و مهاجرت/بازگشت داده‌نگهدار، همگی NOT_RUN هستند. شکست شناخته‌شدهٔ نمونهٔ مثبت Isolation Forest مستقل و بدون تغییر باقی است. این تحویل مجوز ارتقای اجرای زنده نیست.

بازتولید ابزار پایه: `python -B -m viewer_performance.capacity.baseline --backend postgresql --counts 32 256 2048 --pairs 2 --out qualification/capacity-baseline.json`؛ اتصال فقط از متغیرهای محیطی آزمایش PG18 گرفته می‌شود. تولید zip خصوصی مالک، از source پین‌شدهٔ PR30 و با `--project` است. برای بازگشت این بستهٔ صرفاً اندازه‌گیری، توقف ابزار و حذف فایل‌های خروجی خودش کافی است؛ هیچ migration یا تغییر cursor محصول ندارد. روش بازگشتِ نامزدهای بعدی جدا آزموده خواهد شد.
