# نمونهٔ مستقل رفتار فشرده

تصمیم مالک و مدیر در ۲۱ نوامبر: حفظ لاگ خام، روابط مالی، مدل‌ها و ساختار ذخیره‌سازی قبلی الزام محصول جدید نیست. این پوشه اولین دروازهٔ این تصمیم است: **Elasticsearch یا فایل کامل → استخراج در حافظه → رفتار فشرده در PostgreSQL**. پیش از بازنویسی کامل UI و AD، همین مسیر روی سرور مالک اندازه‌گیری می‌شود.

این نمونه، نسخهٔ نهایی محصول نیست. UI و AD جدید، Baseline و آماده‌سازی مدل، alias محدودکننده و آزمون تاریخچهٔ بزرگ هنوز پیاده/پذیرفته نشده‌اند. برنامهٔ موجود هنگام benchmark متوقف و سپس با ابزار کنترل قبلی بازیابی می‌شود؛ کد اصلی آن درجا ارتقا پیدا نمی‌کند.

## قرارداد `compact-behavior-1`

| فیلد | تعریف و منشأ |
|---|---|
| `behavior_id` | SHA256 قرارداد، stream و RequestID متعارف؛ مستقل از نشست، ورودی و زمان پردازش |
| `request_id` | RequestID منبع؛ برای GUID، قالب متعارف بدون خط تیره و حروف کوچک. شکل‌های اصلی در `state.raw_request_ids` محفوظ‌اند |
| `session_id` | مقدار یکتای Session مشاهده‌شده در همان درخواست؛ GUID متعارف و شکل اصلی در `state.raw_session_ids`. تعارض یا فقدان = NULL؛ هیچ پیوندی با IP ساخته نمی‌شود |
| `api` | مسیر `Core.vN/…` یا `Services.vN/…` پس از حذف suffix شمارهٔ خط؛ چند API متفاوت = تعارض، نه انتخاب دلخواه یکی |
| `observed_at_ns` | زمان لاگ اتمام HTTP عملیات اصلی؛ در نبود آن اولین زمان مشاهده با کیفیت ناقص. نه زمان کلیک و نه الزاماً زمان آغاز درخواست |
| `reported_duration` | مقدار مستقیم ExecutionTime. واحد هنوز UNVERIFIED است و فعلاً مبنای مدل تأخیر نیست |
| نتیجه | Code/symbol فقط از پیام HTTP API اصلی؛ موفقیت گزارش‌شدهٔ G00000/successful، اثبات نتیجهٔ مالی نیست. نتیجهٔ provider جای آن را نمی‌گیرد |
| `kind` | اجرای API مشاهده‌شده؛ AddUserData و GetUserData طبق تأیید مالک automatic_support هستند؛ آغاز دستی برای همه UNKNOWN است |
| ورودی/خروجی | JSON استخراج‌شده با منشأ مشخص، جدا از جدول فهرست/تحلیل؛ پیام خام و رکورد لاگ ذخیره نمی‌شوند |
| ویژگی | نسخهٔ `compact-features-1`؛ هدف‌های ورودی نوع‌دار، مقادیر عددی محدود، اثر ساختار خروجی و وضعیت اعتبار ورودی |
| کیفیت | فقدان، JSON ناقص، تعارض نشست/عملیات/ورودی/خروجی و انتساب provider تأییدنشده صریح‌اند؛ نبود، صفر یا موفقیت تلقی نمی‌شود |

در این gate، تعریف قابل آزمون رفتار «یک RequestID دارای شاهد API عمومی» است؛ **نه شمار کلیک، کاربر یکتا یا تمام اقدامات تجاری محصول**. یکتایی RequestID در stream فرض قرارداد است؛ مشاهدهٔ چند عملیات/اتمام متفاوت، تضاد تولید می‌کند و برای مدل‌ها واجد شرایط نمی‌شود. نمونهٔ فعلی سازوکار تفکیک دو درخواست واقعی با RequestID اشتباهاً یکسان ندارد.

تقدم استخراج: `queryParameters/queryResult` ساختاری از دو procedure مشخص `ud_prc_inquiryInvoiceResult2` و `ud_prc_invoiceRegister`؛ سپس JSON مستقیم API؛ سپس provider دقیق مصوب WaterBills/WaterBillInquiry و GasBills/GasBillInquiry. providerهای دیگر به‌صورت candidate هم‌درخواستی، با `binding_unconfirmed` می‌مانند و برای تحلیل محتوا معتبر تلقی نمی‌شوند. خروجی مرکب چند provider به‌اشتباه خروجی نهایی یک خدمت اعلام نمی‌شود. نام واقعی خدمت پشت InvoiceRegister هنوز حل نشده؛ صرف api عمومی، حل service dispatch نیست.

فراخوانی جانبی `ClientAyanCoPaymentGateway.PaymentInquiry` و `ClientAyanCoCarTax.CarTraverseAddToWatch` جزء payload رفتار اصلی نیست. عملیات عمومی پرداخت اگر API مستقل داشته باشد، مثل سایر APIها یک رفتار مستقل می‌ماند؛ روابط مالی و تحلیل مالی ساخته نمی‌شوند. CacheCoreApi و SQLهای داخلی غیر از دو procedure فوق ذخیره نمی‌شوند. این فهرست اولیهٔ استخراج باید با نیاز روش‌های منتخب تکمیل و پوشش آن آزمایش شود؛ پوشش تمام خدمات یا فیلدها فعلاً تأیید نشده است.

کلیدهای رمز، OTP، token و signature از JSON حذف می‌شوند. JSON توکار ساختاری باز می‌شود. محتوای فیلدهای Base64/imagebytes/filebytes ذخیره نمی‌شود؛ descriptor شامل اندازهٔ متنی و SHA256 جای آن است. این تغییر عمدی قرارداد برای اسناد تصویری است؛ تحلیل پیکسل تصویر جزء نمونه نیست. مقادیر متنی کاربردی و شناسه‌های هدف حفظ می‌شوند.

## ساختار و پردازش

schema پیش‌فرض **`p24_compact`** در PostgreSQL تنظیم‌شدهٔ پروژه است؛ هیچ جدول Viewer یا AD قدیمی خوانده یا نوشته نمی‌شود.

- `behaviors`: یک ردیف فشردهٔ اصلی و ویژگی‌ها؛ PK هویت و دو index نشست/زمان و زمان. index عمومی JSON وجود ندارد.
- `behavior_payloads`: وضعیت استخراج‌شده و ورودی/خروجی با منشأ؛ فاقد متن لاگ، گراف روابط یا تاریخچهٔ تک‌تک شاهدها. فقط وضعیت فعلی/تعارض‌های محدود برای اصلاح دیررس، نه آرشیو raw با نام تازه.
- `pending_requests`: همین وضعیت استخراج‌شده برای RequestID فاقد API در این packet؛ با سقف مشخص.
- `dirty_windows`: اعلان تراکنشی بازپردازش نشست/پنجره؛ اصلاح نشست یا زمان، پنجرهٔ قبلی را هم dirty می‌کند. مصرف‌کنندهٔ AD جدید هنوز ساخته نشده است.
- `streams/windows`: قرارداد، checkpoint مستقل و رسید پنجره. پنجرهٔ ناقص یا gap باعث پیشروی نمی‌شود.

خواندن فایل JSON/gzip و ES صفحه‌ای است؛ raw روی فایل موقت نیز نوشته نمی‌شود. در ES، PIT/search_after با شمار دقیق، ترتیب cursor و کنترل shardها استفاده می‌شود؛ فقط در نبود پشتیبانی PIT به scroll کامل برمی‌گردد. ابتدا تمام مسیرها/levelها خوانده می‌شوند؛ alias و `CallPath.keyword` استفاده نمی‌شود. `_source` به شش فیلد لازم محدود است. صفحهٔ ES حداکثر ۳۲ MiB و رکورد فایل حداکثر ۱۶ MiB است.

گروه‌ها در حافظه، سپس یک خواندن دسته‌ای از وضعیت استخراج‌شدهٔ قبلی، COPY به stage موقت و upsert فقط ردیف‌های واقعاً تغییرکرده انجام می‌شود. رفتار، payload، pending، dirty و checkpoint **در همان تراکنش** ثبت می‌شوند. بازخوانی تکراری همان داده، revision و dirty را زیاد نمی‌کند. اتمام پس از crash و retry از checkpoint قابل ادامه است.

سقف‌های اولیه: ۶۰هزار RequestID در یک پنجره، ۲۵۶ KiB وضعیت هر درخواست، ۱۲۸ MiB مجموع JSON وضعیت استخراج در حافظه، ۳۲ مقدار JSON استخراج‌شده در هر جهت ورودی/خروجی و ۴ variant هویت/اتمام، ۴۰هزار pending و ۵۰۰هزار پنجرهٔ dirty. این اعداد سقف منابع‌اند، نه آستانهٔ آنومالی. عبور از سقف، خطای آشکار و rollback می‌دهد؛ داده بی‌صدا دور ریخته نمی‌شود. RSS شامل overhead اشیای Python و decode صفحه است و می‌تواند بیشتر از سقف JSON باشد. سیاست چرخهٔ عمر pending و مصرف dirty پیش از سرویس پیوسته لازم است؛ cap جای آن‌ها را نمی‌گیرد.

تغییر/حذف یک سند منبع به‌عنوان جایگزینی قطعی نسخهٔ قبلی بازسازی نمی‌شود؛ variant متعارض در وضعیت استخراج، خروجی نامطمئن ایجاد می‌کند. این محدودیت با نداشتن raw history سازگار است و هنوز نیازمند پذیرش/تکمیل قرارداد اصلاح منبع در مرحلهٔ بعد است.

## اجرای gate کوتاه روی سرور Windows

نمونه از شاخهٔ جدا اجرا شود، با Python محیط پروژهٔ نصب‌شده. ابتدا فایل‌های `compact_behavior/` یک بار با manifest خودشان تطبیق داده می‌شوند؛ هش کامل Viewer در حلقه‌ای وجود ندارد. در R2، قبل از توقف نقش‌ها، اولین صفحهٔ منبع به‌صورت فقط‌خواندنی بررسی می‌شود؛ اگر رد شود، ZIP تشخیصی تولید و سرویس‌ها روشن می‌مانند.

```powershell
& 'E:\P24\pishkhan24\.venv\Scripts\python.exe' -X utf8 -B -m compact_behavior.server_trial `
  --project 'E:\P24\pishkhan24' `
  --release-receipt 'E:\P24\pishkhan24\AnomalyDetection\reports\Behavior_Release_20261118_094809_476455df\release.json' `
  --windows 3 --seconds 600
```

دستور از ریشهٔ worktree کاندید و PowerShell ادمین اجرا شود. سقف child آزمون ۱۰ دقیقه است؛ زمان توقف و بازیابی جداست. Taskها، Viewer، AD و وب قدیمی موقتاً متوقف و شرایط قبل، حین و بعد بررسی می‌شوند؛ پس از پایان/خطای کنترل‌شده نقش‌های قبلی بازیابی می‌شوند. هیچ کپی دیتابیس یا benchmark شش‌ساعته‌ای اجرا نمی‌شود. اولین اجرا سه پنجرهٔ کامل اخیر، با فاصلهٔ یک دقیقه از اکنون را می‌خواند. اجراهای بعدی از checkpoint مستقل همین schema ادامه می‌دهند؛ تاریخ پروژهٔ قدیمی جابه‌جا نمی‌شود.

خروجی `Compact_Prototype_*.zip` شامل `prototype.json`، `trial.json`، هویت package، شمار و کیفیت رفتار، زمان دریافت/استخراج، خواندن قبلی، ساخت ویژگی، نوشتن و Commit، RSS اوج، اندازهٔ جدول‌ها و شمارنده‌های backend PostgreSQL است. زمان source_request_decode شامل درخواست، دریافت پاسخ و decode JSON است و داخل read/extract هم وجود دارد و دوباره به آن اضافه نشود. شمارنده‌های I/O ممکن است عقب‌تر از پایان باشند؛ حجم خواندن PostgreSQL معادل قطعی دیسک فیزیکی نیست. زمان child شامل instrumentation سنگین cProfile یا tracemalloc پیش‌فرض نیست؛ tracemalloc فقط با انتخاب صریح فعال می‌شود.

برای اجرای مستقل روی فایل‌های کامل، بدون ابزار کنترل قدیمی:

```text
python -m compact_behavior --config CONFIG.py --stream explicit-source-name --files FILE1.json.gz FILE2.json.gz --output REPORT.json
```

در قطع کامل کنترل‌کننده، همان ماژول `server_trial` با `--project … --restore-receipt PATH_TO_TRIAL_JSON` طرح قبلی را بازیابی می‌کند. هویت child از nonce و زمان ایجاد process بررسی می‌شود. نتیجهٔ خروجی‌گرفتن و راه‌اندازی مجدد سرویس‌ها، تأیید کامل AD نیست.

## شواهد مرحلهٔ اول و gate بعدی

آزمون محلی PostgreSQL 18.6: چهار فایل واقعی ۲۰ اکتبر، مجموع **۳۴۹۹۱۰ لاگ → ۷۴۰۵۲ رفتار API عمومی**. مجموعهٔ RequestIDهای مستقل شمرده‌شده دقیقاً با رکوردهای ذخیره‌شده برابر بود؛ چهار بازخوانی کامل، صفر INSERT/UPDATE رفتار داشتند. زمان هر پنجره در این اجرای محلی حدود **حدود ۸ تا ۸٫۶ ثانیه** بود؛ schema تازه و بدون AD/وب/دریافت زنده ES. این نتیجه، سرعت سرور مالک یا آزمون تاریخچهٔ بزرگ نیست و به‌عنوان جهش سرعت تولیدی اعلام نمی‌شود. oracle، شمار شناسه‌ها را تأیید می‌کند، نه معنای تمام پارامترها و کفایت کامل payload خدمات.

۵۶ آزمون محلی شامل PostgreSQL واقعی، COPY، crash واقعی process قبل/بعد commit، دیررس، تعارض، concurrency، idempotence، PIT و scroll، HTTP واقعی محلی، خواندن ناقص فایل، retry گزارش Windows و منطق stop/restore موفق‌اند. در سه اجرای ناقص مالک، بازیابی چهار نقش بدون خطا ثبت شده؛ دریافت و انتشار کامل ES واقعی مسیر جدید، ظرفیت بزرگ و تازگی AD هنوز **NOT_RUN** هستند. CI ویندوز/PG جدا گزارش شود؛ آزمون mock کنترل نقش، جای اجرای زنده نیست.

پس از خروجی کوتاه سرور، ابتدا کمبودهای استخراج و bottleneck همین مسیر بررسی شود. سپس UI نشست/رفتار و AD مستقل با قرارداد و مدل تازه ساخته شوند. روش‌های قابل بررسی از دادهٔ جدید: نرخ/تکرار، ترکیب خدمت، تنوع هدف ورودی تأییدشده، نتیجهٔ گزارش‌شده، ساختار پاسخ معتبر و توالی عملیات. مدل زمان پاسخ پس از تأیید واحد/معنای مدت؛ روش‌های SQL داخلی و روابط مالی خارج از دامنه‌اند. هیچ روش یا Baseline قدیمی صرفاً با تغییر نام منتقل نمی‌شود؛ تا کافی‌شدن مرجع، نتیجه صریحاً دادهٔ ناکافی است.

اهداف بعدی مدیر: بیش از ۱۲ پنجره در ساعت با AD و وب و بدون رشد عقب‌ماندگی؛ p95 تأخیر تحلیل کمتر از پنج دقیقه پس از انتشار؛ هدف ۶۰–۱۲۰ پنجره در ساعت برای جبران تاریخچه؛ برابری روی دادهٔ نمایندهٔ دورهٔ نگهداری. هیچ‌یک از این اهداف از نمونهٔ کوچک پذیرفته نشده‌اند.

## پیگیری اجرای مالک و گزارش پاسخ Elasticsearch — R2

اجرای مالک در `Compact_Prototype_20261121_083125_46e100fa.zip` پس از حدود ۱٫۵ ثانیه با `elastic_partial_page` پایان یافته است؛ هنوز هیچ رفتار/پنجره‌ای ثبت نشده، cursorهای قدیمی در آزمون تغییر نکرده و هر چهار نقش و پراکسی بدون خطای بازیابی برگشته‌اند. این نتیجه، آزمون سرعت نیست. نسخهٔ R1 جزئیات کدام شرط پاسخ را نگه نمی‌داشت؛ علت دقیق رد پاسخ از آن ZIP معلوم نمی‌شود و نباید timeout، شکست shard یا اشکال شکل پاسخ را قطعی فرض کرد.

R2 جزئیات پرچم‌های timed_out/terminated_early، حضور/نوع فیلدها، شمار shardها و علت دقیق رد، total hits و روش پیمایش را ثبت می‌کند؛ سندها و PIT IDها وارد گزارش تشخیصی نمی‌شوند. شرط کامل‌بودن پاسخ ضعیف نشده است. پنجرهٔ فعال نیز پیش از خواندن در رسید ثبت می‌شود. استخراج، هویت رفتار، schema و قواعد ویژگی تغییر نکرده‌اند.

برای گرفتن دادهٔ لازم بدون توقف سایت یا اتصال PostgreSQL:

```text
python -m compact_behavior.probe_elastic --project E:\P24\pishkhan24 --start 2026-11-21T08:15:00Z
```

این دستور نسخهٔ ES و فقط یک صفحهٔ جست‌وجو با size=1 را می‌خواند و cursor را می‌بندد. خروجی یک `Compact_ES_Probe_*.zip` است. موفقیت صفحهٔ اول، کامل‌بودن کل پنجره نیست. بازهٔ 08:15 UTC، اولین پنجرهٔ محاسبه‌شده از زمان شروع child در اجرای ناموفق است؛ نسخهٔ R1 آن را پیش از خواندن ثبت نکرده بود. پس از تشخیص علت واقعی، آزمون کامل ادامه می‌یابد.

## دریافت مقاوم پنجره — R3
