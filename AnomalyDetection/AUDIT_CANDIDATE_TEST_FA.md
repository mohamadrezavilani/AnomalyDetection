# کاندید اصلاحی AD — آزمون ایزولهٔ ۱۰ نوامبر ۲۰۲۶

این بسته کاندید اصلاح است و پذیرش Production ندارد. هیچ نیاز به نصب، Reset یا تغییر تنظیمات PostgreSQL ایجاد نمی‌کند. روی کپی جداگانهٔ پروژه آزمون کنید. تغییرات فقط در AnomalyDetection هستند؛ Viewer و P0 آزمایشی تغییر نکرده‌اند.

## گزارش از نصب موجود بدون تعویض سورس Worker

خطای خواندن baseline_process.json اکنون گزارش‌گیری را متوقف نمی‌کند. پس از سه تلاش محدود، قفل واقعی مستقل حفظ می‌شود؛ هویت غیرقابل‌خواندن UNKNOWN می‌ماند، heartbeat جای هویت را نمی‌گیرد و گزارش PARTIAL_EVIDENCE_BUNDLE_EXPORTED با جزئیات امن ساخته می‌شود. این اصلاح، ACL سیستم‌عامل را تغییر نمی‌دهد. اجراهای Start و Stop نیز با هویت ناشناخته مسدود می‌شوند.

برای گزارش‌گیری از Worker در حال اجرا، فایل‌های پوشهٔ نصب را با git pull یا کپی فایل جایگزین نکنید: Worker تغییر Manifest را RELEASE_CHANGED می‌شناسد و خاتمه می‌یابد. checkout جدا بگیرید و با همان Python محیط نصب اجرا کنید. core.autocrlf=false بایت‌های Manifest را هنگام checkout ویندوز حفظ می‌کند:

```powershell
git clone --config core.autocrlf=false --config core.eol=lf --depth 1 https://github.com/mohamadrezavilani/AnomalyDetection.git E:\P24\AD-Report-20261110
python -B E:\P24\AD-Report-20261110\AnomalyDetection\Collect_Acceptance_ReadOnly.py --project E:\P24\pishkhan24 --seconds 60
```

اگر مسیر نصب شما متفاوت است، فقط --project را مطابق آن تغییر دهید؛ checkout نیز باید پوشه‌ای جدید و جدا از نصب باشد. ابزار خودش Manifest گزارش‌گیر را تأیید می‌کند، کد نصب را اجرا یا عوض نمی‌کند، دیتابیس را فقط با نقش AD و اتصال READ ONLY می‌خواند و ZIPها را در reports نصب می‌نویسد. شناسهٔ گزارش‌گیر، Manifest نصب و هویت مشاهده‌شدهٔ Worker از هم جدا هستند. کد خروج ۲ با مسیر output یعنی گزارش ناقص ساخته شده و باید همان ZIP بررسی شود؛ به معنای توقف Worker یا پذیرش پروژه نیست. نبود مجوز خروجی reports یا خواندن اعتبارنامه همچنان می‌تواند جمع‌آوری را محدود کند و مجوزها خودکار تغییر نمی‌کنند.

## آزمون فوری بدون دیتابیس

از پوشهٔ AnomalyDetection اجرا کنید:

```bash
python -B validation/qualify_audit_candidate.py --output reports/audit_candidate
```

خروجی قابل ارسال `reports/audit_candidate/qualification.zip` است. کد خروج ۲ یعنی آزمون‌ها با محدودیت باز گزارش شدند؛ فایل qualification.json و شکست Oracle را بخوانید. شکست شناخته‌شدهٔ سناریوی Isolation Forest حفظ می‌شود؛ مدل در مثبت دیگری فعال است. امتیاز آن احتمال تقلب یا تضمین کشف هر جهش نیست. کد خروج ۱ شکست جدید یا ناقص‌ماندن مجموعه است. کد صفر نیز فقط دامنهٔ آفلاین را تأیید می‌کند.

## آزمون PostgreSQL واقعی در محیط تست مستقل

محیط این ممیزی postgres، psycopg و Flask آماده نداشت و چیزی نصب نشد. آزمون بومی این بسته هنوز NOT_RUN است. از PostgreSQL و psycopg 3 **از قبل موجود** در محیط تست استفاده کنید. ابزار هرگز سرور، نقش یا دیتابیس ایجاد نمی‌کند؛ ابتدا باید یک دیتابیس خالی و جداگانه با نامی مانند p24_audit_fixture و پورت مستقل داشته باشید.

فایل اتصال خصوصی خارج از مخزن:

```json
{
  "isolated_audit_database": true,
  "connection": {
    "host": "127.0.0.1",
    "port": 55432,
    "dbname": "p24_audit_fixture",
    "user": "EXISTING_TEST_ROLE",
    "password": "LOCAL_TEST_PASSWORD"
  }
}
```

```bash
python -B validation/qualify_audit_native.py --config /PATH/TO/private-test-config.json --output reports/audit_candidate/native.json
```

اتصال به p24_design_viewer، میزبان غیرمحلی، پورت ۵۴۳۲، override اتصال و schema موجود AD رد می‌شود. ابزار جدول‌های Fixture و ماژول AD را فقط داخل یک تراکنش می‌سازد و در پایان rollback می‌کند؛ دادهٔ موجود را پاک نمی‌کند. schema موجود را با Drop یا Reset دور نزنید؛ دیتابیس تست مستقل لازم است. Fixture هیچ اتصال به Viewer واقعی ندارد.

دامنهٔ ابزار بومی: SQL واقعی پنج مسیر نمونهٔ خدمت، currentness، پروفایل دیررس/منتظر refresh، خروجی پرونده و مسیر scenario_worker.step با Source صریحاً مصنوعی. این ابزار تأخیر واقعی Elasticsearch، UI مرورگر، بازیابی پس از crash، رقابت چند Worker، ظرفیت و دقت برچسب‌خوردهٔ Production را تأیید نمی‌کند. خروجی native.json را پس از اجرا در کنار qualification.zip ارسال کنید؛ فایل اتصال را ارسال نکنید.

## تغییرات و حد اعتبار

مرجع categorical frequency، کیفیت شاهد، تفکیک scope و سقف مرجع تحویل قبلی حفظ شده است. اکنون پروفایل جاری باید Fact معتبر، نسخهٔ مطابق و صف refresh خالی داشته باشد. رفع refresh حتی با بدنهٔ یکسان، مصرف‌کنندگان را دوباره صف‌بندی می‌کند. مسیر چندروزه نیز پروفایلِ منتظر بازپردازش را از شاهد و مرجع کنار می‌گذارد.

روش عددی جدید، جدایی کاملِ میانهٔ هر نشست را در دو جهت با رتبهٔ جایگشتی و تصحیح تعدد مقایسه بررسی می‌کند؛ حداقل ۳ نشست جاری و ۲۰ نشست مرجعِ جدا لازم است. شیفت‌های جزئی، وابستگی میان نشست‌ها، تغییر نسخهٔ مجاز و علت مالی همچنان به بررسی مستقل نیاز دارند.

روش سناریو و evaluator اصلی نسخه‌دارند. نتایج روش قبلی تا بازبینی جاری شناخته نمی‌شوند. شناسهٔ مدل به نسخهٔ پیاده‌سازی وابسته است تا رسید مدل قدیمی برای الگوریتم جدید استفاده نشود. Worker کاندید، کارهای تکمیل‌شدهٔ روش قدیمی را در دسته‌های محدود دوباره صف‌بندی می‌کند؛ نشانگر بازبینی v3 مستقل از نشانگر تکمیل‌شدهٔ v2 است و primary_version معتبر حفظ می‌شود. این تغییر روی سرویس زنده اجرا نشده است.

R3 تاریخی و ترکیب دقیق R3 + فایل R3.1 ارائه‌شده، با digest کامل مستقل شناخته می‌شوند؛ ترکیب دوم ۱۸۰ فایل و viewer_data با SHA256 برابر 603d90df89184dc0625966541a59fdfbb656a1c278b7191d418c7822df5ad4bb دارد. Snapshot هش واقعی را حمل می‌کند. تغییر حتی یک فایل اضافی رد می‌شود. پذیرش این ترکیب، تطبیق کامل نصب سرور یا پذیرش SQL/ظرفیت آن نیست.

در این مرحله فرمان نصب یا راه‌اندازی Worker روی Production اجرا نکنید. بسته برای آزمون ایزوله آماده شده است؛ نتایج بومی و طرح مشخص انتشار/برگشت باید پیش از تغییر سرویس زنده بررسی شوند.
