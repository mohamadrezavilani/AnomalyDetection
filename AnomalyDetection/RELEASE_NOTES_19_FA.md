Build: AD-PRODUCT-20261104-19. PostgreSQL تنها backend؛ منبع pinned: 9bc58af3b0b75cdb880426560f6c7e69fd0b0d6269ef28ba91f85bc65814a97b. تمام تغییرها در AnomalyDetection و schema خودش هستند؛ public، Viewer، LogManagment، Core/پرداخت و checkpoint منبع دست‌نخورده‌اند.

مشکل: نرخ فراخوانی، همان قبضِ تکرارشده یا تغییر معنای پاسخِ موفق را به‌تنهایی نشان نمی‌داد؛ درخواست‌های فنی هم الزاماً رفتار تجاری canonical نبودند. راه‌حل: ویژگیِ دارای منشأ از ورودی/خروجی اصلی، مرحله‌های مشاهده‌شده و IP ریشهٔ client، همراه مرجع مستقل و مسیر جداگانهٔ درخواست فنی. شرح ۹ سناریو و حدود دقیق در SCENARIO_COVERAGE_19_FA.md است.

- request_profiles: فقط SELECT در snapshot تکرارپذیر، با raw reader/parser خود Viewer؛ اصل موضوع از BillUniqueID/InvoiceUniqueID تفکیک می‌شود. fieldهای Auth/Trace/Session و شناسهٔ فاکتور، موضوع قبض نیستند. شناسه‌ها و متن پاسخ به fingerprint تبدیل می‌شوند؛ raw/credential در پروفایل جدید ذخیره نمی‌شود.
- scenario_models: تکرار همان موضوع، تنوع ورودی/شناسه، تغییر IP همراه محتوای غیرمعمول، پیمایش چند خدمت، حذف مرحلهٔ آموخته‌شده، تغییر ساختار/معنای پاسخ، نتیجهٔ ناموفق، تغییر دوطرفهٔ حجم و رفتار چندنشستی. فقط الگوی مشاهده‌شده گزارش می‌شود؛ تقلب/مالکیت/علت قطعی/کسر پول از لاگ ناکافی نتیجه نمی‌شود.
- scenario_traffic: census صفحه‌ای درخواست root شامل API فنی؛ staging و fence انتشار اتمیک، صفر فقط با پوشش کامل. شمارش درخواست فنی، رفتار تجاری جدید نمی‌سازد. هویت ناقص، درخواست را از حجم حذف نمی‌کند و به نشست جعلی تبدیل نمی‌شود. تاریخچهٔ منبع به‌صورت دوره‌ای مرور می‌شود؛ اصلاح نمونه و حذف scope قبلی نامعتبر می‌شوند.
- scenario_store/worker: صف مستقل پایدار، سهم تازه/تاریخی و استخراج مستقل، timeout/backoff محدود بدون افزایش بودجهٔ منبع. ذخیرهٔ مدل/receipt، کنترل نسخه هنگام commit، quarantine مرجع و حفظ کیس/feedback. صف جدید نتیجهٔ آمادهٔ primary را dirty نمی‌کند. ظرفیت زنده نیاز به سنجش دارد.
- scenario_web: /scenarios و /scenario-evaluation/<scope>، روش/دلیل/مرجع/field یا مرحلهٔ تغییرکرده و شاهد Viewer؛ وضعیت ناکافی/صف صریح. نمای تجمیعی خدمت و کاربران قبلی و کلید پایدار پرونده حفظ می‌شوند.
- case-review04: تصمیم و صف سناریو، نمونه/تعداد پروفایل، پروفایل شاهد پرونده و مدل متناظر؛ حد۶۰ثانیه/۲۵۶MiB و PARTIAL صریح. بدون خواندن raw از Viewer و بدون تغییر مدل هنگام export.

نصب، منبع قبلی را آرشیو و فقط سرویس AD را راه‌اندازی می‌کند؛ داده، مدل‌های نرخ، feedback و شناسهٔ پرونده حفظ می‌شوند. baseline محتوا خودکار از دادهٔ واقعی گرم می‌شود؛ خالی/ناکافی بودنِ اولیه، عادی بودن رفتار نیست. Python والد همان محیط موجود مالک استفاده شود؛ Downloads منبع اجرای دائمی نیست.

۱۴۸ unit PASS، قراردادهای قبلی SQL/Worker/HTTP، مسیرهای content/network جدید و نصب/ارتقای ایزوله در validation ثبت می‌شوند. PostgreSQL/WASM ایزوله، پذیرش Windows PostgreSQL مالک یا سنجش precision/recall/ظرفیت تولید نیست. برای پذیرش واقعی، صفحهٔ /scenarios و خروجی case-review همین نصب لازم است. هیچ تضمین کلی برای کشف همهٔ آنومالی‌ها یا درستی مالی اعلام نمی‌شود.
